# Library contract (the seam)

This file is the **one agreement** between the backend (writes the library) and the two UIs (read it).
Nobody changes this contract alone. If a ticket needs a change, stop and report it; the main session updates this file, the schemas, `packages/core` and the fixture together.

- JSON Schemas: [`schemas/`](schemas/) (one per file type; the source of truth for field names).
- Shared UI logic that implements the read side: [`packages/core`](../../packages/core/).
- A complete example library: [`fixtures/library/`](../../fixtures/library/) (generated by `fixtures/make_fixture.py`).

## 1. Principles

1. **Two copies of a source, no more.** `original.*` (what was downloaded, never changed) and `content.md` (the Markdown the model read). Cards, the reader and the copy prompt all **point into `content.md` by line number**. No source text is copied anywhere else.
2. **Line numbers are the reference system.** 1-based, inclusive ranges, on `content.md` split by `\n`. `content.md` is **immutable** once written.
3. **Pages and timestamps are a lookup, not a copy.** `meta.json` maps line → page (PDF) or line → seconds (video) as short run lists.
4. **One writer per file.** The backend writes everything except `state/`, `notes/`, `inbox/` and `topics.yaml`. Each device writes only its own `state/<device_id>.json`. This avoids Syncthing conflicts.
5. **Small to load.** A UI starts with 2 files (`library.json`, `cards.json`). To show a few lines it reads **only the bytes between two anchors** of `content.md` (a few KB), using the `[line, byte]` anchors in `meta.json`. The whole `content.md` (≈1 MB for a 400-page book) is loaded only for the book view.

## 2. Folder layout

```
library/                              ← the Syncthing folder
├─ library.json                       backend   manifest: generation, source list, topic list
├─ cards.json                         backend   every card (one file)
├─ tag_suggestions.json               backend   open topic suggestions from the model
├─ topics.yaml                        user      your topic tree; the backend only reads it
├─ reports/
│  ├─ latest.json                     backend   last ingest run (checks per source)
│  └─ <run_id>.json                   backend
├─ sources/<source_id>/
│  ├─ original.pdf | original.html | original.info.json (+ original.<lang>.vtt)
│  │                                  backend   ground truth, moved (not copied) from inbox/
│  ├─ content.md                      backend   the Markdown the model read — immutable
│  ├─ meta.json                       backend   toc, line→page / line→time, asset list
│  └─ assets/…                        backend   images referenced from content.md
├─ state/<device_id>.json             device    read-state, known, my tags, split marks, prompt, topic decisions
├─ notes/<card_id>.md                 user      one Markdown note per card
└─ inbox/                             user      drop files here; add URLs to inbox/links.txt (one per line)
```

The backend's private working data (embeddings, checkpoints, merge history, original cards of merged cards) lives **outside** the library on the GPU machine. The library holds only what the UIs need.

### Write rules
- Backend writes each file as `name.tmp` then renames it (atomic). Readers ignore `*.tmp` and Syncthing temp files (`.syncthing.*`).
- Backend writes `library.json` **last** in every batch, with `generation` + 1. UIs reload `cards.json` / `tag_suggestions.json` / `reports/latest.json` when `generation` changes. `cards.json.generation` must equal `library.json.generation`; if it is lower, the UI waits and retries (sync still in flight).
- Devices write their state file debounced (≤ 1 write per second) and atomically where the platform allows.
- Syncthing conflict copies (`*.sync-conflict-*`) of a note are shown to the user; of a state file they are merged like any other device file.

## 3. `content.md` conventions

| Thing | How it appears |
|---|---|
| Encoding | UTF-8, `\n` line ends. Line 1 = first line. |
| Headings | Markdown `#`, `##`, `###`. Also listed in `meta.json.toc` with their line. |
| Images | On their **own line**: `![caption](assets/fig-003.png)` — path relative to the source folder. Also listed in `meta.json.assets`. |
| Math | `$…$` inline and `$$…$$` display (KaTeX). |
| Code | fenced ```` ``` ```` blocks. |
| Video transcript | One cue per line: `[m:ss] text` or `[h:mm:ss] text`. YouTube chapters become `##` headings. Slide frames are image lines at their time. |
| Page breaks | **Not** in the text. Use `meta.json.pages`. |

## 4. Files

Field-level definitions are in the schemas. Summary:

### `library.json` — [schema](schemas/library.schema.json)
```json
{ "schema_version": 1, "generation": 42, "updated_at": "2026-09-27T03:10:00Z",
  "sources": [ { "id": "s_booka", "kind": "pdf", "title": "Interpretability Notes", "authors": ["A. Author"],
                 "origin": { "filename": "interp-notes.pdf" }, "added_at": "…", "status": "ready",
                 "n_lines": 1700, "n_cards": 9, "pages": 43, "keywords": ["Probing", "Features", "Circuits"] } ],
  "topics": [ { "path": "ML/Interpretability/Features" } ] }
```
`kind` ∈ `pdf | blog | video | markdown`. `status` ∈ `processing | ready | failed`. `keywords` = top TOC headings (for search). `origin.url` for web/video sources.

### `sources/<id>/meta.json` — [schema](schemas/meta.schema.json)
```json
{ "schema_version": 1, "id": "s_booka", "kind": "pdf", "title": "…", "original": "original.pdf",
  "content_sha256": "…", "n_lines": 1700, "content_bytes": 61234,
  "anchor_step": 100, "anchors": [ [1, 0], [101, 3252], [201, 6657] ],
  "toc":    [ { "title": "4 · Features", "level": 1, "line": 1190 } ],
  "pages":  [ [1, 1], [41, 2], [81, 3] ],
  "times":  null,
  "assets": [ { "path": "assets/fig-003.svg", "line": 1223, "caption": "Figure 3", "kind": "figure" } ] }
```
- `anchors` (**every source**): `[line, byte]` — the UTF-8 byte offset where that line starts in `content.md`. One every `anchor_step` lines (default 100); the first is `[1, 0]`. This is the index for reading part of the file.
- `pages`: `[start_line, page]` runs sorted by line — page P starts at that line. PDF only.
- `times`: `[line, seconds]` for every transcript line, sorted. Video only.
- To find the page of line L: last run with `start_line ≤ L` (binary search). Same for time.

### `cards.json` — [schema](schemas/cards.schema.json)
```json
{ "schema_version": 1, "generation": 42,
  "cards": [ { "id": "c_0003", "rev": 2, "title": "Superposition",
               "what": "…", "why": "…", "how": "…", "when": "…", "extra": "…",
               "topics": ["ML/Interpretability/Features"],
               "refs": [ { "source": "s_booka", "start": 1201, "end": 1219 },
                         { "source": "s_videoc", "start": 80, "end": 96 } ],
               "images": ["sources/s_booka/assets/fig-003.svg"],
               "created_at": "…", "updated_at": "…" } ],
  "retired": [ { "id": "c_old", "into": ["c_0003"] } ] }
```
- `title` is required. `what/why/how/when/extra` are optional Markdown strings (may contain math).
- `refs` point into `content.md` lines; **no text is stored**. The first ref is the primary one. A card appears in a source's order at its ref's `start`.
- `images` are library-relative paths of assets inside the card's ranges (precomputed so the feed does not open `content.md`).
- `rev` goes up when the text fields change (for example after a merge). **Updated** = device saw an older `rev`.
- `retired`: cards that were merged away or split. UIs move state and notes from `id` to every card in `into`.

### `state/<device_id>.json` — [schema](schemas/state.schema.json)
```json
{ "schema_version": 1, "device_id": "pixel-8", "updated_at": 1759000000000,
  "copy_prompt": { "v": "You are my tutor…", "ts": 1759000000000 },
  "my_tags": { "revisit": { "ts": 1759000000000 }, "old-tag": { "ts": 1759000000001, "deleted": true } },
  "cards": { "c_0003": { "viewed": { "rev": 2, "ts": 1759000000000 }, "explored": { "ts": 1759000000000 },
                         "known": { "v": false, "ts": 1759000000000 }, "tags": { "v": ["revisit"], "ts": 1759000000000 },
                         "split": { "v": true, "ts": 1759000000000 } } },
  "topic_decisions": { "t_0001": { "action": "rename", "path": "ML/Interpretability/Dictionary learning", "ts": 1759000000000 } } }
```
All `ts` are milliseconds since epoch. **Merge rule across device files:** for each field, the value with the highest `ts` wins. `viewed`: highest `rev` wins (tie → highest `ts`). `explored`: earliest `ts` is kept (it is a fact, not a toggle). `my_tags`: per tag, highest `ts` wins (`deleted: true` hides it). The backend reads `split` and `topic_decisions` from all state files.

Derived display state of a card (implemented in `packages/core`):

| Condition | Shows |
|---|---|
| no `viewed` | **New** |
| `viewed` | **Viewed** |
| `explored` | **Explored** |
| `known.v` | **Known** (bold line only) — shown on top of the above |
| `viewed.rev < card.rev` | **Updated** tag |

### `notes/<card_id>.md`
Plain Markdown, the note only. Empty file or missing file = no note.

### `tag_suggestions.json` — [schema](schemas/tag_suggestions.schema.json)
```json
{ "schema_version": 1, "generation": 42,
  "suggestions": [ { "id": "t_0001", "path": "ML/Interpretability/Dictionary learning",
                     "card_ids": ["c_0005", "c_0006"], "reason": "…", "similar_existing": "ML/Interpretability/Features",
                     "created_at": "…" } ] }
```
UIs show a decided suggestion as applied at once (overlay from `topic_decisions`). The backend makes it permanent on its next run: it adds the path to `library.json` `topics`, puts it on the cards, and removes the suggestion. It never edits `topics.yaml`. The topic list the model sees = `topics.yaml` + `library.json` `topics`.

### `reports/latest.json` — [schema](schemas/report.schema.json)
Per run and per source: status, chunk counts, retries, and the four checks (`json_valid`, `ranges`, `overlaps`, `coverage` with `gaps` and `limit`), cards created / merged, splits applied, errors. Optional `overlap_pairs_kept_apart`: `[[card_a, card_b], …]` — same-source cards with overlapping lines that the merge model said are different ideas.

### `topics.yaml`
```yaml
ML:
  Interpretability:
    Features: {}
    Circuits: {}
Mind:
  Focus: {}
```
Up to 3 levels. A topic path is the names joined with `/` (`ML/Interpretability/Features`).

## 5. How a UI reads text (fast path)

1. Start: read `library.json`, `cards.json`, all `state/*.json`. Build maps in memory. (Fixture: < 50 KB. A 50-book library: a few MB.)
2. Need lines 168–181 of `s_booka`: `core.lines("s_booka", 168, 181)` →
   - reads `meta.json` only (small, cached);
   - anchors `[101, 6657]` … `[201, 13550]` bracket the range → reads **bytes 6657–13549** of `content.md` with `LibraryFS.readRange` (web: HTTP `Range`; Android: the `RangeFile` native plugin);
   - splits that piece into lines and returns lines 68–81 of it.
   - If the whole file is already loaded (book view), it slices that instead. A platform without `readRange` falls back to reading the whole file.
3. Page / time of a line: binary search in `meta.json` `pages` / `times`.
4. Copy for deep dive: prompt + card fields + for each ref: `[title — lines a–b, p. x–y]` + the lines. Built by `core.buildDeepDivePrompt()`.

## 6. Search

`core.searchSources(query)` matches, case-insensitive, all words of the query against: title, authors, origin URL, origin filename, kind, keywords, source id. Results ranked: title prefix > title word > other fields. `core.searchAll(query)` also returns cards (title, what) and topics. Opening a source result goes to **P8 Book outline** (phone) / **W2 Reader** (web).

## 7. Versioning

`schema_version` is 1 in every file. A breaking change bumps it; UIs refuse newer major versions with a clear message.
